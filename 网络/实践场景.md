## DNS、CDN
运营商 Local DNS （使用 UDP）存在劫持、跨网调度、缓存刷新不可控三大顽疾。所以现在一般会使用自建或第三方 HTTPDNS，比如阿里云 HTTPDNS，腾讯云 HTTPDNS。

## 长连接

### HTTP 的 Keep-Alive 和 TCP 的 Keep-Alive
HTTP 1.0 在响应完成后，就会关掉连接。HTTP 1.1 支持 keep alive，可以让TCP连接保持一段时间复用。比如 OkHttp 就会用 TCP 连接池管理来支持 Keep-Alive 特性。

TCP 协议本身也有独立的 Keepalive 机制，但和 HTTP Keep-Alive 是两回事。它是传输层（操作系统内核层面）的连接存活检测机制，解决的是「静默断连」问题。

以 Linux 系统为例，当 TCP 连接开启 keepalive 后（操作系统默认通常不开启）：
1. 连接持续空闲达到 tcp_keepalive_time（默认 7200 秒 = 2 小时），内核自动向对端发送一个空的 ACK 探测报文；
2. 收到对端响应 → 连接正常，重置空闲计时器；
3. 没收到响应 → 每隔 tcp_keepalive_intvl（默认 75 秒）重发一次探测；
4. 连续 tcp_keepalive_probes（默认 9 次）都无响应 → 内核判定连接已失效，通知应用层连接断开。

默认情况下，内核不会主动检测「空闲连接」的死活，内核对连接状态完全佛系，只在收发数据时才被动感知；开了配置之后，内核才会定期主动探测，异常连接会被及时识别和回收。所以可以看出来，HTTP的 Keep-Alive 和 TCP 的 keepalive 虽然名字类似，但是含义完全不同，TCP 的偏向于连通性检测机制。

### 连接断开的情况
要实现长连接，自然要先了解什么连接断开的情况：
1. 一端主动关闭连接，主动关闭的一方会发送 FIN，另一端如果去读 socket，将会读到 EoF
2. 应用程序进程崩溃，socket 会由内核关闭，同样会正常发送 FIN
3. 操作系统崩溃，不会发 FIN，对方在尝试读取数据时，最后会 read time out。如果写数据，则是 host unreachable 之类的错误
4. 直接断网，或者说网络发生“静默中断”，而两边都没有进行读写，TCP 连接可能在两边都继续显示为 ESTABLISHED，双方都不知道出了问题。操作系统是否知道会有不同的表现，发送时是成功还是失败，要看操作系统是否已经知道网络不可用。
  * 操作系统立即知道网络断了，例如网卡被关闭、Socket 已经被标记为错误，这时写 Socket 可能立即失败
  * 静默断网，例如 Wi-Fi 仍连接但网络已断、NAT 映射失效、移动网络切换，这时本机操作系统通常不知道数据无法到达服务端，Socket 成功写入内核发送缓冲区就会返回成功。

静默断网，可能的流程如下：
```
应用调用 Socket.write
        ↓
数据成功复制到内核发送缓冲区
        ↓
write 返回成功
        ↓
内核尝试发送 TCP 包
        ↓
收不到服务端 TCP ACK
        ↓
内核不断重传
        ↓
很久以后 TCP 超时
        ↓
Socket 才报告错误
```
TCP 自身会进行多次指数退避重传，最终超时可能达到几分钟，具体取决于操作系统配置。所以对实时性要求高的业务，例如 IM，不能依赖 TCP 自己慢慢超时，所以还需要应用层心跳和业务 ACK。

#### 心跳的作用
长连接的核心矛盾：为什么TCP连接会“假死”（NAT超时、中间设备清理空闲连接、网络波动导致的状态不一致），三大核心问题：连接保活、断线感知、断线恢复。

以 `NAT` 为例：因为 IPv4 的 IP 量有限，运营商分配给手机终端的 IP 是运营商内网的 IP，手机要连接互联网，就需要通过运营商的网关做一个网络地址转换(Network Address Translation，NAT)。简单的说运营商的网关需要维护一个外网 IP、端口到内网 IP、端口的对应关系，以确保内网的手机可以跟 Internet 的服务器通讯。有人测试过国内各家运营商的NAT超时情况，有的运营商在2/3G网络下 NAT 超时是5分钟。

网传的微信智能心跳探测过程大致为：60秒短心跳，连续发3次后开始探测，90，120，150，180，210，240，270。使用固定短心跳直到满足三次连续短心跳成功，则认为这个间隔有效。微信在前台活跃态时，采用了固定心跳机制；在前台熄屏态或者后台活跃态（进入后台10分钟内）时，先用几次最小心跳维持长连接，然后进入自适应心跳机制；在后台稳定态（超过10分钟），则采用自适应心跳计算出来的最大心跳作为固定值。

如果在运行过程中，发生了心跳失败，则执行重连。同时将心跳间隔调整为断线前间隔减去20s，重新走自适应心跳；如果连续5次均失败，则以初始心跳180s继续测试。 参考：https://github.com/Tencent/mars/blob/master/mars/stn/src/smart_heartbeat.cc

> 不过感觉使用固定的时间也没什么问题，只是为了极致优化可用考虑一下这种动态时间间隔的做法

总的来说，就是：
1. Socket 写入成功 ≠ 服务端收到
2. 服务端业务 ACK = 服务端确认接受
3. 接收方 ACK = 接收方确认送达

### 长连接的常见方式
1. 原始 TCP + 私有协议：目前主流的大厂很多都是采用私有协议为主的方式来实现。

2. WebSocket：基于 TCP 实现的全双工通信协议

3. MQTT：基于 TCP 协议，使用“发布 / 订阅”模式，在省流量和扩展性方面都比较突出，MQTT协议中有三种身份：发布者、代理（Broker，可以认为是服务器）、订阅者，发布者与订阅者不直接相连，而是通过服务器解耦通信。发布者和订阅者都是客户端，消息代理是中央服务器，消息发布者可以同时是订阅者。在很多消息推送场景下被广泛使用。

4. XMPP：基于 TCP，传统 IM 协议、XML 格式、较重。现在移动端很少用

5. QUIC：基于 UDP 封装的可靠传输协议

## 以 IM 为例

### IM 业务的可靠传输

#### 确认机制、超时重传
根据前面的介绍，可以知道TCP 协议本身具有 ACK 机制，但为什么还需要业务层的 ACK 机制：发送方的应用层程序，调用 send() 方法返回成功的时候，数据实际是写入到了TCP的发送缓冲区，而非已经被接收方的应用层程序处理。只能借助于应用层的ACK机制。即使数据成功发送到接收方设备了，tcp层再把数据交给应用层后也可能出现异常情况，导致消息在业务层实际是没成功收到的。这种情况下，可以通过业务层的 ACK 来提供保障，确保对方收到了消息。

IM 业务层 ACK 的一种实现方式：IM 服务器在推送消息时，携带一个标识 SID（类似 TCP 的 sequenceId），推送出消息后会将此消息添加到“等待 ACK 的消息列表”，客户端成功接收到消息，会给 IM 服务器回复一个业务层的 ACK 消息，消息中携带有本条接收消息的 SID，IM 服务器接收后，会从“等待 ACK 的消息列表”中删除这条消息，本次推送才算真正成功。IM 服务器的“等待 ACK 的消息列表”一般会维护一个超时计时器，一定时间内如果没有收到客户端回复的 ACK 消息，会从“等待 ACK 的消息列表”中重新取出那条消息重新推送。

服务端推送消息携带的 SID 在本次连接会话中需要唯一，针对同一条重新推送的消息 SID 不变，接收方根据这个唯一的 SID 来对重传的消息执行去重。

> 可以看出来业务层的确认机制、超时重传和 TCP 协议类似

#### IM 服务器宕机重发消息
假如服务器宕机，漏消息了怎么办呢？举一个例子：
1. IM 服务器给接收方推送 msg1，带上最新的时间戳 timestamp1，接收方收到 msg1 后，更新本地最新消息的时间戳为 timestamp1。
2. IM 服务器推送第二条消息 msg2，带上当前最新的时间戳 timestamp2，msg2 在推送过程中由于某种原因接收方和 IM 服务器连接断开，导致 msg2 没有成功送达到接收方。
3. 接收方重连，携带本地最新的时间戳 timestamp1 发给 IM 服务器，IM 服务器会把给接收方暂存的消息中时间戳大于 timestamp1 的所有消息发送过去，其中就包括之前没有成功的 msg2。
4. 接收方收到 msg2 后，更新本地最新消息的时间戳为 timestamp2。

通过这种时间戳机制，接收方可以成功地让丢失的 msg2 补偿发送。不过由于时间戳可能存在多机器时钟不同步的问题，可能存在偏差，所以在实际的实现上，也可以使用全局的自增序列作为版本号来代替。

### 保障消息不乱序
在业务层确保了消息被对方接收，但还有一个问题就是消息的顺序。有的消息先发，但是可能后到，要保证消息的时序一致性，重点就是选择一个时序比较的基准，使消息具备“时序可比较性”。

可以通过两个版本号组成的链表（推送的每条消息携带前一条消息的版本号和当前这条消息的版本号）来检测消息的连续性和时序性。微信的聊天和朋友圈的消息时序也是通过一个“递增”（不保证连续）的版本号服务来实现的，不过这个版本号是每个用户独立作用域的。微博的消息箱则是依赖“分布式的时间相关的 ID 生成器”来对私信、群聊等业务进行排序，目前的精度能保证秒间有序。

服务器先收到到的消息不一定可以先推送到接收方，所以需要客户端整理：接收方收到消息后判定，如果当前消息序号大于前一条消息的序号就将当前消息追加在会话里；否则继续往前查找到恰好小于当前推送消息的那条消息，然后插入在其后展示。每条消息携带前一条消息的版本号和当前这条消息的版本号，实现检测消息的连续性和时序性。

### 客户端的处理

#### 感知断开连接

TCP/WebSocket 只能知道正常关闭，无法凭空感知中间网络已经断掉。尤其是拔网线、路由黑洞、NAT 映射失效等静默断线，在没有任何数据交换时，客户端可能仍显示为 connected。

客户端通常通过以下信号发现：
1. 明确关闭
收到 TCP FIN、RST 或 WebSocket Close，立即知道连接断开。

2. 心跳失败
到下一次 Ping 后仍收不到 Pong，达到超时才认为连接不可用。

3. 主动发送时底层报错
写 Socket 立即失败（比如网卡已禁用），可以判定断开。但“发送 API 返回成功”通常只表示数据写入了本机缓冲区，不代表服务端已收到。

4. 业务 ACK 超时
消息带 messageId/sequence，服务端收到后返回 ACK。超时未收到 ACK，说明消息交付状态未知，通常会将连接标记为可疑并触发探测或重连。

5. 系统网络变化
例如 Wi-Fi 断开、切网，可以提前触发重连，但这只是辅助信号，不能完全代表互联网是否可用。


ACK 超时不一定百分之百说明连接断了，也可能是服务端繁忙、消息处理延迟或 ACK 丢失。因此更准确的语义是：**没收到 ACK，表示消息结果未知，而不是确认发送失败。**

如果没有 FIN/RST、没有网络事件、没有心跳、没有发送行为，也没有 ACK 等交互，静默断开的连接在本地看起来可以一直是“已连接”。连接是否还活着，最终必须通过某种通信来证明。


#### 重连时机
应用层 ACK 超时，可以先重发（例如3次），如果重发多次仍无 ACK，则根据心跳检查连接是否还活着，如果心跳也超时无响应则需要断开旧连接，建立新 TCP 连接。（虽然心跳超时不一定意味着连接断开，但对于 IM 来说，一条几十秒没有响应的连接即使物理上还存在，也已经不能满足实时通信要求，重新建连通常比继续等待更合理。当然，不建议因为一次很短的超时就立即重连，而是再尝试几次ping）


如果连接正常关闭，或者系统立即收到 TCP FIN/RST，通常会马上触发 onDone/onError。如果是拔网线、路由黑洞、NAT 状态丢失这类静默断开，只能靠心跳超时发现。

所以需要在这些情况下重连：
* onDone/onError 立即重连；
* 网络状态变化时立即重连；
* 心跳接收 Pong 超时后指数退避重连；

移动端网络状态件监听
* ConnectivityManager 回调：作为快速预判信号。网络断开回调来了，可以立即将UI切换为"网络断开"，不需要等心跳超时。但网络恢复回调来了，不能直接认为连接可用，必须等心跳确认。监听ConnectivityManager回调，网络切换时不等心跳超时，立即销毁旧连接、发起重连。
* 应用层心跳（PING/PONG）：作为权威判定信号。心跳连续失败N次（通常3~5次），才判定连接真正断开，触发重连。这是最可靠的端到端检测手段。
* Socket IO 异常：作为即时补充信号。如果在正常收发数据时突然抛异常，说明连接已断，立即触发重连，不用等心跳。
UI debounce


```

        ≠
TCP连接状态
        ≠
端到端连接健康度
        ≠
业务Session状态

```

### IM 已读未读
对于高频使用的“总未读”，如果每次都通过聚合所有会话未读来获取，假设会话数比较多，由于需要多次从存储获取，容易出现某些会话未读由于超时等原因没取到，导致总未读数计算少了。而且，多次获取累加的操作在性能上比较容易出现瓶颈。所以，总未读数和会话未读数一般是单独维护的。

不过，单独维护总未读和会话未读能解决总未读被“高频”访问的性能问题，但也会带来新的问题：未读数的一致性。

两个未读的变更不是原子性的，会出现某一个成功另一个失败的情况，也会出现由于并发更新导致操作被覆盖的情况。所以要解决这些问题，需要保证两个未读更新操作的原子性。
* 分布式锁，具备较好普适性，但执行效率较差，锁的管理也比较复杂，适用于较小规模的即时消息场景；
* 支持事务功能的资源，不需要额外的维护锁的资源，实现较为简单，但基于乐观锁的 watch 机制在较高并发场景下失败率较高，执行效率比较容易出现瓶颈；
* 原子化嵌入脚本，不需要额外的维护锁的资源，高并发场景下性能也较好，嵌入脚本的开发需要一些额外的学习成本。

### 多通道优化
用户 A 通过上行通道的短连接网关来发送消息，发送的消息在上行业务处理服务进行存储、加未读等业务操作；然后通过消息队列把这条消息给到下行通道，下行分发逻辑服务查询用户 B 的在线状态等信息，并对消息进行必要的推送准备处理（比如版本兼容处理）；接着把消息给到用户 B 的长连接所在的长连网关机器，长连网关机器再将消息推送到用户 B 的设备中。
这样，我们的上下行通道就通过消息队列的方式进行了隔离和解耦。

对于图片、视频等多媒体消息，由于数据传输量一般都比较大，如果也和普通文本消息收发的通道放在一条连接里，可能会导致消息收发通道出现阻塞，因此我们一般会使用新的连接通道来传输二进制的文件流。这种优化方式除了能保护消息收发的核心通道，也能缩短上传下载的链路，提高媒体消息收发的性能。

在一些即时消息场景的实现中，会通过普通消息收发的长连通道来分片上传语音流，这样更方便通过长连来下推给接收方。另外，IM 服务端在接收到分片后，可以同步先行把分片的二进制流下推给接收方但暂不显示，不需要等所有分片都在后端存储完成再进行下推。

### 其他优化
* 断点续传、分片上传
* 相同图片、视频等资源，可以避免重复上传，但需要服务端判断是否一致，比如用 md5、sha-1，但可能碰撞。比如很简单的办法是：使用多种单向 Hash 算法，在都一致的情况下才判断为重复。
* 服务端（主要）、客户端：各种缓存，提升速度
* 消息收发链路的监控体系搭建

对于长时间没有登录或者消息接收频繁的用户来说，当这些用户下线一段时候后再上线，经常会面临大量的离线消息下推的问题。一种比较好的优化方案是：对多条离线消息采取批量打包 + 压缩的方式来进行下推。

通过这种方式，能够大幅降低传输的数据大小，也能有效减少大量离线消息下推后的 ACK 包数量。但是面对上万条的离线消息，只单纯地采用批量 + 压缩的方式还是不够的，这种情况下，我们还可以采用“推拉结合”的方式来进行优化。用户上线后，对于服务端离线消息的下推，可以只推送用户最近 N 条消息；而对于后续要推送的消息，我们可以让用户通过向上翻页来触发自动拉取，客户端再从服务端来获取当前聊天会话剩下的消息。

另外，在实际的离线消息场景里，我们还需要考虑到离线消息存储成本的问题。绝大部分 IM 系统并不会一直缓存用户的离线消息，而是一般会按照条数或者时间周期，来保留用户最近 N 条离线消息，或者最近多长时间内的离线消息。

## P2P
为什么设备之间不能直接通信，因为互联网上的每台设备需要一个 IP 地址才能互相通信。但 IPv4 地址总共只有约 43 亿个，远远不够全球设备使用。所以现在会使用 NAT（网络地址转换）技术，内网设备主动访问外网时，路由器会把内网 IP 替换成公网 IP，并记录映射关系。外网返回数据时，路由器再根据映射关系转发回内网设备。 

但是这就只允许内网主动向外发起连接，外网无法主动找到内网设备，也就导致了设备之间不能直接通信。目前有常用的方案：UDP 打洞（最常用）、TCP 打洞、端口映射（需要服务器支持，绕过 NAT）、中继转发（打洞全部失败，走服务器中转）。

> 以 UDP 打洞为例，它的原理就是A、B双方都在内网经过NAT向一个服务器发UDP消息，服务器（有专门的程序）会告诉A"B的公网地址"，告诉B"A的公网地址"，然后A可以直接向B的公网地址发消息，B的NAT转换地址到内网后，转发给B，B发消息到A也是同理，不再需要通过中间服务器。这种服务器可以自己开发部署，或者用免费、付费的第三方服务器。

以上方案属于双向对等通信，而如果只是外网的设备想主动和内网的设备通信，则是使用内网穿透。内网穿透的方式如下：
1. 内网设备主动连接公网服务器（TCP或UDP）
2. 外部用户访问公网服务器
3. 公网服务器把请求沿隧道转发给内网设备
4. 内网设备处理请求，结果沿隧道返回

> 内网穿透需要一个专门的服务器用来转发数据，所以成本比P2P更高。

## 推送
很多双向通信的方式都可以用来做推送，这里介绍一个专门的推送协议。

SSE：服务器向客户端单向实时推送数据的 Web 技术。它基于标准 HTTP 协议，响应头的内容类型为 text/event-stream。客户端通过长连接持续接收服务器以事件流形式发送的文本数据，常用于大模型（如 ChatGPT）打字机效果、股票行情和实时日志。

## 登录认证
现在一般使用双Token（Refresh Token + Access Token）。

Token 在客户端本地加密存储，如果自己管理，密钥也要存储，还是容易被破解，所以建议客户端使用系统级安全存储。比如 Android 的 EncryptedSharedPreferences、Keystore，iOS 的 Keychain。因为在系统级安全存储中，密钥的生成和使用全程在硬件安全隔离区内完成，密钥本身永远不会以明文形式出现在应用层内存中。
