# 1.概述
运输层的主要协议：
1. 用户数据报协议UDP（User Datagram Protocol）
2. 传输控制协议TCP（Transmission Control Protocol）

![TCP/IP体系中的运输层协议](https://upload-images.jianshu.io/upload_images/3468445-f07a951524522a49.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

UDP在传输数据前不需要先建立连接。TCP则提供面向连接的服务。

TCP/IP的运输层用一个16位**端口号**来标志一个端口，端口号只具有本地意义。**服务端使用的端口号** 0~49151，**客户端使用的端口号** 49152~65535 仅在客户进程运行时动态选择。

# 2.TCP
套接字 socket = (IP 地址：端口号)
## 可靠传输
三次握手、四次挥手、滑动窗口、拥塞控制（慢启动、拥塞避免）

TCP 要想在 IP 基础上构建可靠的传输层协议，必须有一个复杂的机制来保障可靠性。 主要有下面几个方面：
* 对每个包提供校验和
* 包的序列号解决了接收数据的乱序、重复问题
* 超时重传
* 流量控制、拥塞控制


> 三次握手一是确认双方的收发消息能力，二是各自的状态改变和相应的资源开辟。内核提供的Socket API就是对开辟的资源的操作，开辟的资源主要就是数据缓存，

> 四次挥手，如果中途突然断网，内核有心跳包，超时会自动回收连接和资源

### 停止等待协议、滑动窗口协议
每发送完一个数据单元就停止发送，等待对方的确认，在收到确认后再发送下一个数据单元。由于停止等待协议的信道利用率太低，会使用滑动窗口一次性发送多个数据。

## 异常断连与保活
内核自带 TCP Keepalive 保活机制，但默认周期长达数小时，仅能检测内核层面的连接存活。
开发重点注意：业务长连接必须在应用层实现心跳机制，才能及时感知网络中断、对端进程崩溃、NAT 超时等真实场景的异常。

## MSS / MTU 与分片
数据链路层传输的帧大小是有限制的，不能把一个太大的包直接塞给链路层，这个限制被称为 `MTU` 「最大传输单元（Maximum Transmission Unit）」

IPv4 数据报的最大大小为 65535 字节，这已经远远超过了以太网的 MTU，而且有些网络还会开启巨帧（Jumbo Frame）能达到 9000 字节。 当一个 IP 数据包大于 MTU 时，IP 会把数据报文进行切割为多个小的片段（小于 MTU），使得这些小的报文可以通过链路层进行传输。

TCP 会主动把数据分割成小段再交给网络层，最大的分段大小称之为 `MSS`（Max Segment Size），就是 TCP 的最大分段大小。MSS = MTU - IP header头大小 - TCP 头大小

> 有时候抓包看到的单个数据包大于 MTU，是网卡 TSO 硬件分片特性导致，属于正常现象。

## 粘包
场景：客户端先后发送两段文本 "packet1"（7 字节）、"packet2"（7 字节）
* 预期：服务端分两次收到，各 7 字节
* 粘包：服务端一次收到 14 字节 "packet1packet2"
* 拆包：服务端第一次收到 5 字节 "packe"，第二次收到 9 字节 "t1packet2"

两类问题统称为 TCP 粘包问题，核心本质是：**TCP 协议本身不维护业务消息的边界，只负责按无结构的字节流传输数据**

### 出现场景
TCP 是面向字节流的协议，内核层面只把数据当成一串连续的字节，完全不知道上层业务的 “包” 是如何划分的。

具体触发场景分为三类：
1. 发送端：Nagle 算法主动合并小包
TCP 默认开启 Nagle 算法，为了减少网络中小报文的数量，会将多个短时间内的小发送请求攒在一起，合并成一个 TCP 报文段再发出。比如连续两次 send 各 10 字节，很可能被合并成一个 20 字节的 TCP 包发送。

2. 接收端：缓冲区堆积
TCP 有内核接收缓冲区，到达的数据会先暂存其中，等待应用层读取。如果应用层读取不及时，多个业务包就会在缓冲区里堆叠在一起，应用一次 read/recv 就会读出多个粘在一起的包。

3. 传输链路：MSS 限制导致分段
如果一个业务包的大小超过了 TCP 最大分段长度（MSS，通常约 1460 字节），TCP 会自动把它拆分成多个 TCP 段传输，接收方收到时就是分段的字节流，需要应用层自行拼接。

### 解决方式
1. 消息头 + 长度字段，或者配合复合协议约定（工业级标准，最常用）

2. 特殊分隔符 / 结束符

3. 固定消息长度


## Socket API
使用Socket通信，客户端和服务端会建立连接，类似建立一个通道，然后客户端写数据，服务端读数据。如果客户端写数据，服务端没有读或者读得慢，那么客户端只要写入超过了内核缓冲区可以缓存的大小，就无法再写入，此时写入会阻塞，等到服务端读取了数据后，客户端才能继续写入。

> send/write 调用成功，仅代表数据写入了内核发送缓冲区，不代表对方已经收到，更不代表对方业务层已经处理。TCP 的“可靠”，只保证数据能准确无误、按顺序地到达对方电脑的“内核接收缓冲区”。如何确认对方“处理”了消息，就需要应用层协议（比如HTTP、自定义的IM协议）来自己实现。比如用 TCP 发了消息，只需要等待对方的回应即可，假如网络丢包 TCP 会自动重传，相对来说，如果用下面介绍的 UDP 就不确定是丢包还是网络慢或者对方处理慢，还需要额外的处理。


Socket API 有很多配置选项：
* `TCP_NODELAY`：关闭 Nagle 算法，有数据立刻发送，不等待小包合并，实时性要求高的场景可以考虑关闭（默认会启用 Nagle 算法）
* `SO_RCVTIMEO` / `SO_SNDTIMEO`：读写超时控制，分别设置 recv() 接收、send() 发送操作的最长阻塞时间。默认值：0，代表无限阻塞
* `SO_KEEPALIVE` / `TCP_KEEPINTERVAL`/ `TCP_KEEPCOUNT`：TCP 会在空闲较久时自动向对方发送探测报文，收到响应表示连接正常，重置计时器；假如多次探测无响应，内核就会判定连接已失效，通知应用层连接断开。默认没有开启，内核就不会检测空闲连接是否已断开。（所以这个配置并不是直观以为的保活）
* `SO_RCVBUF` / `SO_SNDBUF`：调整缓冲区大小，高吞吐量场景可适当调大。系统默认开启自动调优，会根据网络情况动态调整。
* `SO_REUSEADDR`：地址复用，允许端口处于 TIME_WAIT 状态时，重新绑定同一个地址和端口。默认值：关闭。适用场景：几乎所有服务端必开。否则程序重启时，会因为端口被 TIME_WAIT 占用而报 “地址已被使用” 错误。？？？
* `SO_LINGER`。控制调用 `close()` 关闭连接时的行为，有三种模式：
  1. 默认模式（l_onoff=0）：close 立刻返回，内核后台把剩余数据发完，正常走四次挥手流程。
  2. 等待模式（l_onoff=1, l_linger>0）：close 会阻塞，直到数据发完或超时。
  3. 强制复位（l_onoff=1, l_linger=0）：close 直接发 RST 复位包，跳过四次挥手，不进入 TIME_WAIT。（可能丢数据）
* `SO_REUSEPORT`：端口复用作用，允许多个 Socket 同时绑定同一个端口，内核自动把进来的连接负载均衡分给各个进程。适用场景：高性能服务端
* `SO_RCVLOWAT` / `SO_SNDLOWAT`（Linux/Android 特有）：控制「缓冲区有多少数据时，才触发可读 / 可写事件」。默认值：1 字节，也就是来至少一个字节才通知应用层。
* `TCP_USER_TIMEOUT`（Linux/Android 特有）： 当连接上有「已发送但未收到 ACK 确认」的数据时，最长等待多久后判定连接失效。默认值：跟随系统 TCP 重传超时（RTO），通常累计好几分钟才会放弃。
* `TCP_QUICKACK`：用于关闭延迟确认（Delayed ACK）机制，收到数据立刻回 ACK，而不是等着捎带在数据包里一起发。默认值：系统默认开启延迟确认（通常等 40ms 左右）。
* `TCP_CORK`（Linux/Android 特有）：强制合并小包，和 TCP_NODELAY 完全相反，强制 “塞住” 连接，把小包攒起来批量发送。
* `IP_TOS`：服务质量标记，在 IP 包头设置优先级标记，告诉中间路由器、交换机优先转发该流量。适用场景：实时音视频、游戏等对延迟敏感的流量，标记高优先级
* `SO_BROADCAST`：广播权限，允许 Socket 发送广播数据包，给 UDP 使用。
* `IP_MULTICAST_*`：UDP 的广播相关配置


## 局限性
* 队头阻塞：单个包丢失时，后续所有已到达的数据都必须排队等待重传，弱网下延迟会急剧上升。
* 连接与 IP 绑定：网络切换（如 WiFi 切蜂窝数据）会导致连接断开，需要重连。
* 仅支持一对一通信，无法实现广播、组播。

# 3. UDP
当实时性很重要，并且不严格要求可靠性的时候，可以选择使用UDP协议。

比如一些场景：
1. 音视频通信：语音/视频通话对延迟极度敏感，人耳对延迟的感知远比对丢包的感知敏感。
2. 实时网络游戏：多人在线游戏中，玩家位置、动作状态需要毫秒级同步。一个位置包丢了没关系，因为马上服务器会发来新的位置数据，等旧包重传过来反而过时了，还会造成画面卡顿
3. 直播流媒体
4. DNS查询等短连接场景：数据即使丢了，应用层直接重发一次即可，成本极低
5. 广播/多播：TCP只支持一对一，而UDP支持一对多。比如IPTV/内网直播、路由协议


UDP本身不可靠，但很多工业级方案选择在UDP之上自己实现可靠性机制，这样既保留了UDP的低延迟优势，又能按需控制可靠程度，例如：
* QUIC（HTTP/3的底层协议）：Google设计，在UDP上实现了可靠传输、拥塞控制、多路复用，还解决了TCP的队头阻塞问题
* KCP：开源的低延迟可靠传输协议，以10%~20%的带宽浪费换取30%~40%的延迟降低，常用于游戏加速
* WebRTC：音视频走UDP+RTP，同时用DTLS加密、SRTP保护媒体流
* RUDP（Reliable UDP）：在应用层加序列号、ACK确认、超时重传

> TCP在内核级优化、网络兼容性、拥塞控制方面有着UDP方案无法复制的优势。UDP上的可靠传输协议（QUIC、KCP）是为了解决TCP在特定场景下的不足（队头阻塞、建连慢、网络切换断连）而生的，它们是对TCP的补充，而不是替代。并且 UDP 可靠协议运行在用户态，数据要经过「网卡 → 内核 → 用户态程序 → 内核 → 网卡」的多次拷贝，还要额外处理应用层的协议逻辑，CPU 开销更高
